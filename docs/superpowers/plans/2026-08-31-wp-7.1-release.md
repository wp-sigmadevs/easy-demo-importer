## 1. Summary

WordPress 7.1 requires **no code changes** to this plugin. Every candidate breaking change was traced to the
call sites in this codebase and ruled out. The compat portion of this release is a one-line readme bump.

That leaves the release slot open for the housekeeping and feature work in §4–§6, which is where the actual
effort should go.

**Baseline unchanged by 7.1:** PHP 7.4 minimum / 8.3 recommended — the same baseline 7.0 set when it dropped
PHP 7.2 and 7.3. `Requires PHP: 7.4` stays correct.

### 3.3 Why client-side media processing cannot engage

CSMP only activates on the REST media endpoint. No import path goes there:

| Path | Call site | REST? |
|---|---|---|
| WXR import | `lib/wordpress-importer/class-wp-import.php:1289` — direct `wp_generate_attachment_metadata()` | no |
| Customizer images | `inc/Common/Models/Customizer.php:186` — `media_handle_sideload()` | no |
| Regeneration phase | `inc/Common/Importer/ThumbnailRegenerator.php:149` — direct call | no |
| Manual import | custom chunked `admin-ajax` action `sd_edi_manual_upload` | no |

The nine `register_rest_route()` calls in `inc/App/Rest/RestEndpoints.php` are all in the plugin's own
namespace; none extend `WP_REST_Attachments_Controller`.

Additionally, `inc/Common/Functions/Actions.php:115` forces `big_image_size_threshold` to `false` during
import, which rules out even the **pre-existing** server-side two-pass sub-size path.

### 4.3 The POT is regenerated by the build — and degraded by it

`webpack.mix.js:101-115` runs `wp-pot` on every Mix build, overwriting
`languages/easy-demo-importer.pot`. The committed baseline, though, was generated by
**`wp i18n make-pot`** (`X-Generator: WP-CLI 2.12.0`). The two disagree, and wp-pot's output is
worse:

| | WP-CLI | wp-pot (build) |
|---|---|---|
| Strings extracted | **509** | 497 — misses the plugin-header metadata entries |
| `X-Domain` | present | **dropped** |
| `Last-Translator` / `Language-Team` / `PO-Revision-Date` | present | **dropped** |
| Copyright / `Project-Id-Version` | plugin name + version | the long plugin *description*, no version |

Regenerated with WP-CLI for the release (`33b62c4`). **This does not survive another build** —
`npm run package` and `npm run zip` both invoke `mix`, so building the release ZIP will silently
re-degrade the file that ships.

Separately, the baseline had drifted badly: **416 strings against 509**. Ninety-three strings added
since it was last refreshed were untranslatable, including the 36 inside
`lib/wordpress-importer/` that carry this plugin's own `easy-demo-importer` text domain.

**Resolved 2026-09-06 (`427af6d`) — option 1.** The `wpPot` block and its `fs.ensureDir` wrapper
are gone from `webpack.mix.js`, along with the `wp-pot` require and the `wp-pot` devDependency.
`npm run translate` now calls `wp i18n make-pot`, the generator that produced the committed
baseline. Translation work now needs WP-CLI, which is the trade accepted here.

Verified: a production build no longer touches the POT (checksum unchanged across a full
`npm run production`), and `npm run translate` is idempotent at 509 strings.

The POT can now be regenerated at any point in the release, not only after the final build.

> This is the third instance of the §4.1 defect class: a build step whose file selection quietly
> did not match what it was supposed to cover. The first two were the eslint and stylelint globs.

### 4.4 The shipped ZIP never contained `uninstall.php` — two bugs, one path

Validating the release artifact (`npm run zip`) surfaced a defect that predates this release and
affects every tagged version since 2.0.0.

**Bug 1 — the file was never packaged.** `webpack.mix.js`'s `includes` array listed
`composer.json`, `index.php`, `readme.txt` and the main plugin file, but **not `uninstall.php`**.
Measured, not inferred: the pre-fix artifact was 1,001,545 bytes across **150 files, containing
zero `uninstall.php`**.

Why that is not cosmetic:

1. `easy-demo-importer.php:54` registers `register_uninstall_hook( ..., [ Setup::class, 'uninstall' ] )`.
2. `Setup::uninstall()` is an **empty stub** — its body is the comment `// See uninstall.php.`
3. All real cleanup lives in `uninstall.php`: every `sd_edi_*` option, the `_transient_sd_edi_*`
   pairs, `sd_edi_taxonomy_import`, `sd_edi_import_log` and the restore-point shadow tables.
   (This originally also claimed `sd_edi_import_cron` events — no such hook exists; see §4.5.)
4. WordPress prefers `uninstall.php` when present, and otherwise fires the registered hook.

With the file absent, deletion fell through to the empty stub: **the shipped plugin cleaned up
nothing.** This contradicts the 2.0.2 changelog line "Uninstalling removes leftover restore-point
shadow tables instead of orphaning them" and `IMPROVEMENTS.md` #6, which marks uninstall
✅ Done and notes it is required for premium-marketplace submission.

**Bug 2 — and the cleanup was broken anyway.** The table teardown ran through
`$wpdb->prepare()` with a `%1$s` placeholder for the table name. `prepare()` treats that as a
*string* placeholder, so the identifier is quoted as a literal and the statement is a syntax
error — the tables are never removed. The line already carried a
`phpcs:ignore ...PreparedSQLPlaceholders.UnquotedComplexPlaceholder`, so the linter had flagged
exactly this and been silenced.

This is the `$wpdb->prepare()` identifier anti-pattern already recorded for
`SnapshotManager` on the `alpha` branch — the same bug, independently, on `master`.

Fixed by matching the codebase's own convention at `inc/Common/Utils/Snapshot.php:402`:
interpolate the backticked identifier and skip `prepare()` entirely. `%i` would be the modern
answer but requires WP 6.2+, above this plugin's declared 5.5 floor. Every name involved is built
from `$wpdb->prefix` or returned by `SHOW TABLES`, so none of it is user input.

> Had only Bug 1 been fixed, uninstall would have shipped and still silently left both tables
> behind. Validating the artifact is what exposed the pair.

**Also absent from the ZIP:** `LICENSE` — added in the same pass. Not a functional defect, since
`readme.txt` and the plugin header both declare GPLv3, but the licence *text* was never
distributed with the plugin. GPLv3 expects the terms to travel with the work, so the 35 KB
`LICENSE` at the repository root now ships too.

### 4.5 Multi-lens review — what it caught

Three independent reviewers (security, performance, correctness) over `master...HEAD`, each
finding verified against the code before acceptance. **3 MUST FIX, 9 SHOULD FIX, 1 dropped.**

Every MUST FIX was in `uninstall.php` — code §4.4 had just promoted from never-executed to live.
Shipping it was right; it also meant a file that had never run in production was suddenly running
in production, and it had real bugs:

| # | Defect | Consequence |
|---|---|---|
| 1 | `MediaSnapshot` never discarded, and the `sd_edi_mediasnap` option deleted first | An open restore point's media half — in `move` mode, the site's **entire pre-import uploads tree** at `wp-content/sd-edi-restore/` — stranded on disk with nothing referencing it |
| 2 | `$wp_filesystem->rmdir()` called unguarded | `WP_Filesystem()` returns false without populating the global under WP-CLI or `FS_METHOD=ftpext`; fatal on PHP 8, aborting deletion after the DB cleanup had committed |
| 3 | Cron cleanup named `sd_edi_import_cron` | No such hook exists anywhere. The real one, `sd_edi_manual_cleanup`, is scheduled **daily** and survived deletion, firing forever against a deleted callback |

Fixed together: `MediaSnapshot::discard()` now runs before the option sweep (reusing the tested
path rather than reimplementing it), the filesystem call is guarded to match `Finalize.php:207`,
and cron cleanup uses `wp_clear_scheduled_hook()` — which clears every occurrence, unlike
`wp_next_scheduled()` + `wp_unschedule_event()`. `_sd_edi_source_url` postmeta is now swept too;
it is written per imported attachment and nothing had ever removed it.

**Multisite is a documented limitation, not a fix.** WordPress runs `uninstall.php` once, in the
context of the blog deletion was triggered from, so a network-activated install cleans exactly one
blog. Recorded in the file's docblock; the `get_sites()` + `switch_to_blog()` loop belongs with the
multisite work in §7, not bolted on here.

**`phpcs.xml` `/lib/*` exclusion reversed.** The commit that added it said "scope the ruleset to
code we own", but `lib/wordpress-importer/` *is* code we own: 21 first-party commits in six months,
including `76cffcf fix(security): sanitize imported SVGs to prevent stored XSS`. With PHPStan's
`paths:` set to `inc` only, ~3.4k lines of security-sensitive WXR parsing had no static analysis at
all. Measured before changing anything: the security and DB sniffs report **zero** violations there,
so coverage was restored at no cost — only the six style/metrics/docs sniffs the upstream code
legitimately trips are excluded, and only for that path.

**A defect I introduced while fixing the same defect class.** §4.3 replaced the POT build step with
`npm run translate`, and that command did not exclude `dist/` — which `npm run package` fills with a
complete copy of the plugin. Reproduced with a probe string, which duly appeared in the POT. Running
translate after package would have doubled every source reference. This is the fourth instance of
the over-broad-file-selection class named in §4.1, and the first one authored here rather than
inherited.

**The a11y fix had traded one defect for another.** Replacing `<label>` with `<div>` did fix the
missing accessible name, but `<button>` is a labelable element, so the wrapper had been forwarding
clicks — the row stopped toggling while `_cp-regenerate.scss` still styled it as clickable. And the
`aria-labelledby` target wrapped the tooltip icon, whose antd `role="img"` label folded into the
name ("Force all sizes **info-circle**"). Both now fixed: `<label>` restored, the id moved to a
text-only span, the icon `aria-hidden`, and `jsx-a11y/label-has-associated-control` configured with
`controlComponents: ['Switch']` so the linter stops pushing toward the version that breaks clicking.

**Dropped on verification:** a SHOULD FIX claiming ~31 MB of dev dependencies ship in the ZIP.
Measured the real artifact instead: `vendor/` is **200 KB**, the classmap **8,416 bytes / 74
entries**, zero PHPUnit/Mockery/PhpParser. `npm run package` already runs `composer install --no-dev`
before the copy. The reviewer measured the post-restore working tree and flagged the caveat itself.

**Changelogs corrected.** Both 2.0.3 entries were written before §4.4 was found, so the release's
most user-visible fix was missing from them, and the published 2.0.2 line claiming uninstall removed
shadow tables stood as a false claim. Both now state what actually happened.

**Verified in the rebuilt artifact**, not just the working tree — 1,016,993 bytes, 152 files,

### 4.6 Security review — findings and the one fix taken

Full-codebase pass anchored to OWASP, tracing every entry point (20 Ajax actions, 9 REST routes)
and each injection / file / network / deserialization sink to its source. **0 critical, 0 high,
0 medium, 2 low.**

Clean, and several controls are above baseline: all REST routes gate on `manage_options` through a
single `permission()` with no `__return_true` anywhere; every `unserialize()` passes
`['allowed_classes' => false]`; `RemoteUrl::get()` forces `redirection => 0` and re-runs the full
SSRF guard on **each** hop rather than trusting the first URL; both extraction sites carry ZipSlip
guards; and the SVG path gates `upload_mimes` *and* `fixSVGDetection()` on the same capability with
a comment naming CVE-2024-9071 and warning they must stay identical.

**Fixed — rejected requests now leave a trace.** Both denial paths in `Helpers.php` returned `403`
and wrote nothing, while the plugin ships a perfectly good activity log; a probe against the admin
endpoints was invisible afterwards.

The routing is the part worth recording. The obvious implementation — write every denial to
`ImportLogger` — is wrong here: `ImportLogger::getRuns()` groups by `session_id` and caps the view
at ten runs, and `recentRunRows()` does not filter empty ones. Session-less denial rows would
collapse into a single phantom "run" and push real imports out of the Activity tab. It would also
hand any authenticated low-privilege user a way to drive unbounded table writes by spamming a
rejected action. So denials during an import attach to that run (an expired nonce mid-import is
exactly the "page left open too long" case the error text describes), and denials outside one go to
`error_log()`, which is host-rotated and cannot bloat the database. `sd/edi/security_denial` fires
in both cases so a site can route them anywhere.

Two `LOW` findings were left alone, both deliberately:

- **`react-router-dom` carries two moderate advisories, neither reachable.** No SSR anywhere in the
  admin app, so the `deserializeErrors()` hydration issue cannot fire; the open-redirect vector has
  no dynamic target (zero `useNavigate` call sites, `createHashRouter`). Resolves with the React
  Router 7 major already deferred in §6.
- **A ZipSlip hardening gap**, not a vulnerability: the guard rejects `..` and absolute paths but
  not a Windows drive-letter prefix. Not raised as a finding because it cannot be tied to a concrete
  attack — the archive comes from the theme's own config or an admin's upload, and both actors
  already have code execution. Worth one line if that function is ever touched.

## 5. Features — 7.1-native integration

### 5.1 Abilities API — *recommended, highest value*

Register the importer's operations as first-class abilities on `wp_abilities_api_init`, making the plugin
drivable by AI agents and MCP clients. No competitor in this space (OCDI, Merlin WP, TI One Click) has this.

Proposed surface:

| Ability | `public` | Rationale |
|---|---|---|
| `easy-demo-importer/list-demos` | `true` | Read-only, safe to expose |
| `easy-demo-importer/import-status` | `true` | Read-only progress polling |
| `easy-demo-importer/import-demo` | `false` | Destructive — writes content, can reset the DB |
| `easy-demo-importer/rollback` | `false` | Destructive |

Notes for implementation:
- 7.1 adds a **unified `public` exposure flag**, defaulting to `false` when not supplied. Set it explicitly on
  every ability rather than relying on the default, so intent is legible.
- 7.1 extends `wp_get_abilities()` with filtering by category, namespace, or metadata.
- Guard registration with `if ( ! function_exists( 'wp_register_ability' ) ) { return; }` — the plugin still
  supports WP versions without the API.
- `permission_callback` must gate on the same capability the equivalent AJAX handler uses. **Do not** let an
  ability become a path around an existing capability check.
- The destructive abilities must respect the `SessionManager` mutex exactly as the AJAX handlers do.

### 5.2 SVG Icon API — *optional*

7.1 adds `wp_register_icon_collection()`, `wp_register_icon()`, `wp_get_icon()`, plus REST routes
(`/icon-collections`, `/icons`, `/icons/<collection>`). The plugin already bundles `enshrined/svg-sanitize`
and ships custom SVGs, so demo configs could register icon sets as a first-class import artifact.

Lower value than §5.1. Only worth doing if a theme partner actually asks.

### 5.3 Sequencing recommendation

Ship §5.1 as **2.1.0**, not in the compat release. A compat tag should be small and boring so it can go out
fast; the Abilities work deserves its own QA pass.

committable change by themselves; the durable artifacts are the regenerated PHPStan baseline, the
autoloader, and one new pin.

**PHPStan baseline shifted, as predicted.** `php-stubs/wordpress-stubs` moved 6.9.1 → 7.1.0, which
sharpens several core return types, so ten previously-invisible errors surfaced — five stale
`ignore.unmatched` entries plus five "always true / always exists" narrowings. None are real bugs:
they are defensive guards that the sharper stubs can now prove redundant *on 7.1*, but which still
matter on the older versions `Requires at least: 5.5` admits. Baseline regenerated rather than
code changed — 153 → 154 suppressed errors across the same 91 entries.

**One real regression, and it was pre-existing.** The eslint gate died outright with
`Cannot read properties of undefined (reading 'Intrinsic')`. Cause: `@wordpress/eslint-plugin`
declares an unconstrained `typescript` range, which resolved to **7.0.2**; TS 7 removed
`ts.TypeFlags.Intrinsic`, which `ts-api-utils@1.4.3` (pinned under `@typescript-eslint@6.21.0`)
reads. Because the lockfile is gitignored, **any clean `npm install` would have hit this** — it
was a latent landmine, not something the update introduced.

Fixed at the root by pinning `typescript: ^5.9.3` in `devDependencies`, which constrains every
consumer in the tree at once. Pinning `@wordpress/eslint-plugin` back instead would have left
`typescript` unconstrained, so a fresh install could still pull TS 7 via `stylelint`'s
`cosmiconfig`. eslint returned to exactly its pre-bump state: 0 errors, the one known
`react-hooks/exhaustive-deps` warning.

**`npx update-browserslist-db` was skipped deliberately** — it only writes the lockfile, which is
not tracked, so it would produce no committable change.

⚠️ **`composer update` regenerates the autoloader unoptimized**, wiping the committed classmap
(−539 lines). `composer dump-autoload --optimize` was re-run before committing. This is the §8
gotcha, and it fires on every dependency change, not just at release time.

## 7. Multisite — out of scope, but needs a decision

The multisite feature exists entirely on the unmerged `origin/multi-site` branch. It is **not** affected by
7.1 (both 7.1 multisite tickets are core-internal), so there is no reason to force it into this release —
but it should not be left to rot either.

**Branch state as of 2026-08-31:**

| | |
|---|---|
| Last commit | `2d95fef`, 2026-07-08 |

| Declared target | v1.2.0 (readme, PR doc and QA doc all say 1.2.0) |
| Size | 43 files, +5087 / −94 |
| Merge conflicts | **14 files** (via `git merge-tree`) |
| QA | `docs/superpowers/qa/2026-04-29-multisite-1.2.0-qa.md` — 5 envs × 20 cases, **entirely unfilled** |

Master today has almost no multisite awareness: three `is_multisite()` call sites total
(`inc/App/Rest/RestEndpoints.php:844`, `inc/Common/Models/DBSearchReplace.php:77-82`).

**Conflicting files:** `easy-demo-importer.php`, `Finalize.php`, `Initialize.php`, `RestEndpoints.php`,
`ImporterAjax.php`, `Helpers.php`, `Setup.php`, `uninstall.php`, `ModalComponent.jsx`, `Setup.jsx`,
`Success.jsx`, `readme.txt`, `readme.md`, `__components-dir.scss` (plus vendor autoload, regenerated).

The new files (`ContextResolver`, `NetworkInstaller`, `UploadSkipCounter`, `App/Network/*`, `NetworkStatus`,
the network React app) merge cleanly. **Textual conflicts are the cheap part.**

**The expensive part is semantic staleness.** The branch predates most of 2.0, and everything master added
since is multisite-unaware:

- **Snapshot / rollback** — the branch's QA matrix literally marks this *"Phase 4 only — N/A for v1.2.0"*.
  It is on master now. Snapshot tables and options need per-blog scoping. Per project notes this feature
  has not had full live QA even on single-site.
- **`SessionManager` mutex** — site-scoped or network-scoped? Two subsites importing concurrently is a case
  the branch never considered.
- **`log_callback` sink / `wp_sd_edi_import_log`** — the branch hooks `wp_initialize_site` /
  `wp_uninitialize_site` for per-blog table creation, but master has added tables and options since.
- **Manual import (chunked zip upload)** — newer than the branch. `UploadSkipCounter` only covers the WXR
  attachment path.
- **`Preflight.php`** — the branch routes through `ContextResolver::canRunImport`; master's `Preflight` is
  newer and independent.
- **`uninstall.php`** — both sides rewrote it.

**Recommended sequencing:** rebase onto master as its own effort, retarget the docs 1.2.0 → 2.1.0, audit the
above for blog scoping, then run the QA matrix in full. The matrix is not optional: a DB reset scoped to the
wrong blog wipes a live subsite, which makes this the highest-blast-radius code in the plugin.
